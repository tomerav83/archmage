# UX resilience pass (UX)

Every state a user can reach must have a defined screen. "It works when the
data is there" is one of four cases.

| ID | Check | How to verify | Default sev |
|---|---|---|---|
| UX-01 | Four states per async path | Each fetch/read/import has loading, empty, error and success rendering — any of the four left unhandled is a finding, loading included. Exception: an operation that cannot block perceptibly has no loading state to render and is judged on the other three — a synchronous `localStorage` read, and equally an `await` over a **local, size-capped** source (a `File.text()` under an enforced cap, an in-memory parse). The loading state is required once the operation crosses the network, is unbounded in size, or can take more than a frame | major |
| UX-02 | Errors are caught at a boundary | An error boundary wraps the app and any third-party/complex subtree; a throw in one widget must not blank the page | blocker |
| UX-03 | No silently swallowed failures | Mechanical: an **empty** `catch` body, a `catch` that only logs, `.catch(() => {})`, or an ignored rejection. An empty catch is a `FAIL` even when an enclosing function returns a message for the *outer* operation — nested swallows are the common case, so verdict each `catch` block on its own, and a message that implies the swallowed step succeeded makes it worse, not better. The single `PASS` shape is a catch whose failure has no user-visible consequence, said so in an inline comment. **UX-03 owns the swallow.** When one empty `catch` also implicates UX-04 (message quality) and UX-07 (work at risk), report it here only — UX-04 judges messages that are actually shown, UX-07 judges data loss with no failure to swallow | major |
| UX-04 | Error messages are actionable | The bar: the message names the thing that failed. A message built from the app's own validator text passes; one that interpolates a caught exception's `.message` verbatim (a `SyntaxError`, a stack, an HTTP code alone) fails. **Carve-out:** a top-level error-boundary fallback may show the raw `.message` as diagnostic detail and still `PASS`, provided the surrounding copy names what broke and offers a recovery action | minor |
| UX-05 | Errors clear | Find every site that resets the error state. Clearing it only on the *next success of the same operation* is a `FAIL` — the message then survives every unrelated edit in between. `PASS` needs a reset on the next user action, a dismiss control, or a timeout | minor |
| UX-06 | Destructive actions are recoverable | Delete/overwrite/reset either confirms first or offers undo; a destructive control is not the default-focused or adjacent-to-primary button | major |
| UX-07 | Work is not lost | Persistence failures (quota exceeded, private mode, corrupt stored value) are caught and surfaced; leaving/reloading with unsaved work warns; a failed import does not destroy current state | blocker |
| UX-08 | Stored state is version-tolerant | Data read from storage is validated and falls back to a clean default rather than crashing the app when the shape changed | blocker |
| UX-09 | Concurrent sessions do not corrupt | Two tabs writing the same key: last-write-wins clobbering is acknowledged, or `storage` events reconcile | minor |
| UX-10 | Form fields validate what they emit | **Scope: values typed into the app's own inputs only** — validation of parsed/imported data belongs to SEC-06, do not report it here. The bar is the data, not the polish: a field that can emit `NaN`, `undefined` or a wrong type into the model is a `FAIL`. Fields that coerce correctly `PASS` even with no inline messaging | major |
| UX-11 | Async actions cannot double-fire | Submit/save/import buttons disable or guard while in flight; rapid repeat clicks do not queue duplicates | major |
| UX-12 | Optimistic updates roll back | UI applied before confirmation reverts on failure and tells the user | major |
| UX-13 | Stale results cannot overwrite newer state | Any path that can be started twice before the first finishes — a file read, a fetch, a debounced save — must sequence its results (request id, `AbortController`, or a guard). Two in-flight reads where the slower one wins is a `FAIL` regardless of how fast the operation usually is | minor |
| UX-14 | The empty first run makes sense | A brand-new user with no data sees guidance, not a blank canvas or a broken layout | minor |
| UX-15 | Failure handling is centralised, then localised | Two halves, both required where they apply. (a) Remote failures are handled once — an interceptor or query-layer `onError` that notifies the user and handles auth expiry — rather than each call site inventing its own toast; `N/A` if the app makes no requests. (b) Error boundaries are placed per-subtree, not only at the root: a route, a third-party widget or a heavy panel that throws should degrade in place. A single root boundary that blanks the whole app on any throw is a `FAIL` here (UX-02 covers *having* a boundary at all; this check is about granularity — do not report the same defect twice). **Verdict on the halves that apply:** if (a) is `N/A` because the app makes no requests, judge the row on (b) alone and say so in the `Where` cell — the row is not `N/A` while a half still applies | major |
